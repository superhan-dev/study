# OMS와 PII간 설계

현재 두 서버간의 관계는 2PC (2 phase commit)으로 두개의 서버가 강결합되어 하나만 문제가 있더라도 서비스 전체가 문제가 생기는 현상이 발생할 위험이 존재한다.

예를 들어 OMS에서 주문을 수집시 PII에 문제가 발생하면 해당 처리 때문에 다른 주문들도 수집을 못받은 경우가 발생한다.

이 때문에 하나의 서버에서 문제가 발생하더라도 반대 서버에서는 자신의 역할을 계속해서 이어나가는 것이 중요하다.

두개 서버의 책임은 각각 다음과 같다.

- OMS 책임
  1. 주문을 수집한 뒤 미처리주문부터 활성 주문까지 처리되도록 한다.

- PII 의 책임
  1. MSA로써 주문에 사용되는 개인 정보 저장하고 조회할 수 있도록 제공한다.

위 책임들을 2PC로 구현할 경우 분산 트랜젝션에서 원자성은 보장하지만 성능의 오버헤드가 크고 준비/커밋 사이 잠금을 유지하기 때문에 지연이 발생한다. 또한 네트워크 문제가 발생하면 복구의 난이도가 증가한다.

각 서비스는 다른 서버의 상태와 상관없이 각자의 책임을 처리할 수 있어야 한다.

이 때문에 결합도를 낮추는 작업이 필요하다.

결합도를 낮추는 방법으로 다음 두가지 방법이 존재한다.

1. Saga 패턴 활용
2. Outbox 패턴 활용

# Saga 패턴

사가 패턴의 아이디어는 다음과 같다. 전체를 하나로 묶지 않고 각 서비스는 자신의 DB에 먼저 커밋하고 실패하면 되돌리는 보상 트랜잭션을 사용한다.

- 사가의 보상 트랜잭션 종류
  - 보상 후 종료
  - 보상 후 재시도
  - 보상 없이 재시도만

비즈니스 성격에 따라 위와 같은 케이스들이 나뉜다.

# 제한적인 한계 설계

카프카가 없고 레디스를 사용할 수 있는 경우 다음과 같은 설계를 할 수 있다.

## 1. 핵심 원칙

1. OMS DB 트랜잭션 안에서 주문 저장 + outbox 저장(원자성)
2. outbox를 Redis Stream으로 퍼블리시 한다.(비동기)
3. PII는 Stream consumer group으로 소비하고 처리
4. 중복 재시도는 멱등성 키로 방어
5. 성공 결과는 콜백 or Redis 응답 채널로 OMS에 전달
   1. -> orders.cii_id 업데이트

## 2. OMS 트랜잭션 (A DB)

주문 생성 시 다음과 같이 처리한다.

- orders 생성 (cii_id NULL, cii_status=PENDING)
- outbox 레코드 생성
  - type=PII_CREATE_REQUESTED
  - idempotency_key = order_id (또는 outbox_id)
  - payload (최소 데이터/참조키)

### 2.1. outbox 테이블을 분리하는 이유

orders의 pii_id, pii_status와 outbox의 데이터는 1대1이다. 그렇다면 그냥 orders 테이블을 조회해서 outbox 테이블 없이 사용하면 되는것 아닌가? 라는 질문이 생긴다.

하지만 outbox테이블이 비효율적으로 orders테이블에 읽기 요청이 발생하고 쓰기 요청때는 일시적인 lock이 많이 발생한다. 때문에 outbox 패턴을 분리하는 것이 좋다.

outbox 테이블은 스캔/락/업데이트 부하를 orders 테이블에서 분리하고 재시도 및 에러추적을 보다 편하게 해주는 효과가 있다는데 가치가 있다.

위와 같은 큐 테이블에서 쿼리를 하게되면 워커는 다음과 같이 동작한다.

- 처리 대상 찾기: `status=NEW/RETRY` 이고 `next_retry_at <= now()`인 것.
- 오래된 것부터(공정성) ORDER BY next_retry_at, id
- N 개만 처리: LIMIT 100
- 여러 워커가 경쟁하므로: `FOR UPDATE SKIP LOCKED`로 가져오기
  - `FOR UPDATE SKIP LOCKED`로 쿼리를 하면 이미 처리중인 다른 워커(스레드)가 잡고있는 row(LOCKED)된 쿼리는 생략하고 조회하게된다. 불필요하게 처리된 row를 조회할 필요가 없기 때문에 성능상 이점이 있다.

이 처럼 새로 생긴 row이거나 재처리가 필요한 row를 잡아 워커가 조금씩 자주 처리할 수 있도록 특정 개수를 설정해 처리가 되도록 설계하는 것이 dequeue의 정석이다.
